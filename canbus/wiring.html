Crosstrek CAN Tap

Wiring a CANable 2.0 to a 2024 Subaru Crosstrek: what to build, what to verify on the bench, and how to read the first six seconds of traffic.

Vehicle 2024 Crosstrek · 3rd gen Adapter CANable 2.0 · candleLight Stack SocketCAN / gs_usb
01

Prove the hardware on the bench

Two adapters arrived, which is exactly what a bench test wants. Link them to each other and confirm frames cross before the car is involved. If this fails in your kitchen, you do not want to be debugging it in a driveway with the ignition on.

This is also the one time the 120 Ω termination jumpers go on. A standalone CAN segment needs a terminator at each physical end — two jumpers, 60 Ω across the pair. Remember you did this, because step 03 turns them both back off.

# terminal 1 — bring both up at 500k, normal mode (bench only)
sudo ip link set can0 type can bitrate 500000 && sudo ip link set can0 up
sudo ip link set can1 type can bitrate 500000 && sudo ip link set can1 up

# terminal 2
candump can1

# terminal 3 — should appear in terminal 2
cangen can0 -g 100

Confirm CAN FD works too, since a 2024 platform may need it. If this command errors, your firmware is not an FD build and you will want to reflash before the FD probe means anything:

sudo ip link set can0 type can bitrate 500000 dbitrate 2000000 fd on
02

Build the DE-9 to OBD-II cable

Three conductors, and one you deliberately leave out. The adapter uses the standard CiA 303-1 DE-9 CAN pinout; the car uses SAE J1962.

SignalDE-9OBD-IINotes
CAN-H 76Twist with CAN-L
CAN-L 214Twist with CAN-H
Ground 35Signal ground; pin 4 is chassis, acceptable fallback
+12 V 916Do not connect — power the adapter from USB

Twist the CAN-H and CAN-L conductors together over the length of the cable. This is a differential pair; untwisted flying leads next to an engine bay pick up noise you will later mistake for data.

Verify before you plug in

Connector orientation is the single easiest thing to get backwards, and the numbers molded into the shells are the authority — not this drawing. Continuity-test the finished cable with a multimeter, DE-9 pin to OBD-II pin, before it goes near the car.

Why pin 16 stays disconnected

OBD-II pin 16 is battery positive and live with the key out. Feeding it into a USB-powered adapter that shares ground with your laptop creates a second path to vehicle ground — a ground loop that can inject noise, and in the bad case put vehicle current somewhere it was not meant to go.

Run the laptop on battery, not on a charger sharing building ground, for the same reason.

03

Turn the termination jumpers back off

The vehicle bus is already a properly terminated segment: 120 Ω at each end, 60 Ω across the pair. Your adapter is joining in the middle as a listener, not extending the end of the bus. Adding a third terminator drops the bus to roughly 40 Ω, which degrades signal integrity for every module on it.

You can confirm it from outside: with the ignition off and the adapter unplugged, measuring resistance across OBD-II pins 6 and 14 should read near 60 Ω. Around 120 Ω means one terminator is missing or you are on a segment that is not what you think it is.

04

Read the first six seconds

Ignition on, engine off, then run the probe. It sweeps classic 500k, CAN FD at two data rates, then the slower body-bus candidates, listen-only throughout. What matters is not just whether frames appear — it is what the CAN controller's error state says when they don't.

cd canbus && ./bringup.sh

Modules go to sleep after a few idle minutes. If everything reads silent, cycle the ignition and run it again before concluding anything.

05

If the port is gatewayed

This is the outcome that decides how large the project is, so establish it before investing in captures. Bring the interface up without listen-only and send a standard diagnostic request. A reply with no other traffic is the signature of a gateway that passes request-and-response but filters out everything the modules broadcast to each other.

# normal mode — needed to transmit the request at all
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 && sudo ip link set can0 up
candump can0 &
cansend can0 7DF#0201050000000000   # request coolant temp
06

Once traffic is flowing

The capture and analysis tooling is on the branch. The pattern for isolating any control input is the same: record nothing happening, record one thing happening, diff.

# baseline — touch nothing
./capture.sh baseline -t 60

# one control, actuated repeatedly
./capture.sh avh-button -t 60 -n "pressed x8"

# bits that took a value never seen at rest
tools/event_diff.py logs/baseline-*.log logs/avh-button-*.log

# how much of an existing Subaru DBC actually applies
tools/decode.py --dbc subaru_global_2017_generated.dbc logs/baseline-*.log

Nothing the diff prints is a result until it reproduces. Re-run both captures, watch the candidate live with cansniffer -c can0, and capture the inverse action to confirm the bit clears.

Still read-only

Everything above listens. Transmitting to make a feature turn itself on at startup is a separate design problem with real prerequisites — rolling counters, checksums, which module arbitrates the request, and what happens when a replayed frame and the physical button disagree.

On a 2024 car the chassis and EyeSight messaging is still being worked out by the community, and a module that latches a fault has no undo. Finish the capture work first; it is a prerequisite either way.

Pin assignments per SAE J1962 (vehicle diagnostic connector) and CiA 303-1 (DE-9 CAN). Verify against the numbering molded into your connectors and continuity-test the cable before use. Tooling lives in canbus/ on claude/crosstrek-canbus-setup-wu6290.
